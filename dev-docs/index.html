Balanced text wrapping

Applied globally on html in styles.css (it's an inherited property, so every heading and paragraph on the site gets it automatically). It makes lines break evenly instead of leaving a single lonely word on the last line. Supported in all current major browsers; unsupported browsers just ignore it and wrap normally. Browsers also cap the effect to a handful of lines for performance, so very long paragraphs fall back to normal wrapping past that point.

html {
  text-wrap: balance;
}

Headings need an explicit line-height

body sets a global line-height (see "Body line-height tightened to 1.45" below), tuned for paragraph text. Any selector that doesn't set its own line-height inherits that value — fine for body copy, too loose for a large IBM Plex Serif heading, especially once it wraps to two lines.

First caught on .stats-header h2, .benefits-header h2, and .cta h2: they matched .products-header h2 in family, size, and weight but never set their own line-height, so they rendered visibly more spaced-out than the other section headings on the same page. A full sweep of every selector setting font-family: 'IBM Plex Serif', serif' across all 11 stylesheets turned up 57 more with the same gap. All 60 now set an explicit line-height: 1.3 for section-level headings (~1.75rem and up), 1.35 for card-level h3/h4 (~1.1–1.75rem), and 1 for the handful that are single numerals or initials centered in a fixed-size shape (.step-number, .team-card-photo-placeholder, .groceryaisle-hero-nav-number).

.cta h2 {
  font-family: 'IBM Plex Serif', serif;
  font-size: clamp(2rem, 4vw, 2.75rem);
  font-weight: 600;
  line-height: 1.3;   /* was missing — inherited body's line-height instead */
  color: var(--white);
  margin-bottom: 1.5rem;
}

Rule of thumb for new headings: section-level h2 (~2–3rem) → 1.3. Card-level h3/h4 (~1.1–1.75rem) → 1.2–1.4, tighter as the size grows. Set it every time a selector declares font-family: 'IBM Plex Serif', serif' — don't rely on the inherited default.

Body line-height tightened to 1.45

Sitewide default in styles.css changed from line-height: 1.6 to line-height: 1.45 — a deliberate design call for tighter paragraph leading, not a bug fix.

body {
  font-family: 'Inter', sans-serif;
  background-color: var(--cream);
  color: var(--text-primary);
  line-height: 1.45;   /* was 1.6 */
  overflow-x: hidden;
}

Headings are unaffected — every IBM Plex Serif heading now sets its own line-height explicitly (see above), so none of them were riding on the body default. This change only reaches selectors that still inherit rather than declare their own line-height: mainly plain paragraph text and any component that never overrode it. Most body-copy selectors across the site already set an explicit 1.5–1.8 of their own, so this mainly affects untouched paragraphs and any other text that was quietly riding the old 1.6 default — worth a visual pass across pages to confirm nothing reads too tight.

H1/H2/H3 unified into shared type-scale tokens

An audit of every heading on the site (11 stylesheets) found each page had independently invented its own H1/H2/H3 sizes over time. H1 alone had 9 different scales across 10 templates. H2 was worse: at least 6 different clamp ceilings and 3 different line-heights for what is visually the same "section heading" role. H3 was mostly fine — it already clustered around two values — but had a handful of drifted outliers. None of this was a deliberate design decision; it was accumulated drift from each page being built independently against copy-pasted CSS.

Fixed by introducing shared tokens in styles.css's :root (loaded on every page) and pointing every heading selector at them instead of a hand-rolled value:

:root {
  --h1-size: clamp(2.25rem, 4vw, 3.5rem);
  --h1-line-height: 1.15;

  --h2-size: clamp(1.75rem, 3vw, 2.5rem);
  --h2-line-height: 1.3;
  --h2-compact-size: clamp(1.5rem, 3vw, 2rem);   /* card/list-level H2s */
  --h2-compact-line-height: 1.3;

  --h3-size: 1.25rem;       /* default H3 */
  --h3-lg-size: 1.35rem;    /* more prominent H3 (team names, benefit titles) */
  --h3-line-height: 1.35;
}

.page-hero-title,     /* Contact Us, Our Team, Privacy, Terms, Why Breez, Our Story */
.hero-title,           /* Home */
.groceryaisle-hero-title-main,
.demo-visual-title,    /* Book Demo */
.blog-hero h1,
.article-title {
  font-size: var(--h1-size);
  line-height: var(--h1-line-height);
}

H1 dropped from the homepage's old 4.5rem/72px ceiling (the single biggest H1 on the site) to one shared 3.5rem/56px ceiling used everywhere, including pages that previously had their own one-off scale (Grocery Aisle, Book Demo, both blog templates). H2 collapsed 6 drifted scales into two: --h2-size for section/CTA headings, --h2-compact-size for card- and list-level headings that are legitimately smaller by role (newsletter card, legal .terms-heading repeated per-section, blog category headers) — not everything became one number, because those really are a different visual tier. H3 consolidated onto the two sizes that already dominated (1.25rem default, 1.35rem for more prominent titles).

Two of the old hardcoded-breakpoint-stacked-on-a-clamp bugs (see the "balanced text wrapping"-style antipattern first caught on the homepage hero) turned up again during the sweep and were removed the same way: Book Demo's .demo-visual-title (H1) and .demo-form-title (H2) each had a redundant font-size override at 768px stacked on top of their clamp — deleted, since the clamp's floor already covers that width.

Deliberately left out of the token system — these aren't drift, they're a genuinely different role and forcing them onto the shared scale would be a regression, not a fix:

  • .groceryaisle-feature-title (H3) and .groceryaisle-section-title's extra breakpoint-narrowing rules — Grocery Aisle already has its own well-built, progressively-tightening clamp() system tuned across 4 breakpoints; only its base (>1080px) declaration now points at --h2-size, the narrowing rules underneath are untouched.
  • .blog-card-featured .blog-card-title — the one prominent card in the blog grid is supposed to read bigger than a normal post card.
  • .form-section-title (Book Demo) and .contact-method-content h3 — these are small in-form/in-list field labels, not content headings a reader scans.
  • .terms-subheading — legal-doc sub-label, weight 700 and no serif family, a deliberately different treatment from a real H3.
  • .visual-card-front/back h3 (Why Breez) — decorative flip-card micro-titles.

Also found, not fixed here (flagging rather than silently changing scope): Grocery Aisle's actual <h1> contains only the logo <img> — there's no visible H1 text on that page at all. The big visible headline ("Let's make shopping easy and inspiring") is a <p class="groceryaisle-hero-mainheadline">, not a heading. .groceryaisle-hero-title-main/-accent, .product-card-title, .coming-soon-title, and .groceryaisle-widget-title are all dead CSS — not referenced by any current markup — left tokenized in case they come back into use, but worth a cleanup pass on their own.

Rule of thumb for new headings: use var(--h1-size) for a page hero, var(--h2-size) for a real section/CTA heading, var(--h2-compact-size) only for a heading nested inside a card/list/repeated-block, and var(--h3-size) / var(--h3-lg-size) for H3. Don't invent a new clamp for a heading that's filling one of these roles — and never stack a hardcoded pixel-breakpoint override on top of a clamp-based token.

Favicon files live in /favicon

All favicon assets (android-chrome-192x192.png, android-chrome-512x512.png, apple-touch-icon.png, favicon-16x16.png, favicon-32x32.png, favicon.ico, site.webmanifest) are grouped under the /favicon folder. Every page links them explicitly via absolute paths, so add new pages with the same block.
